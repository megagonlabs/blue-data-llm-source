# Compatibility

What this library does differently from the LLM source in the Blue monolith, and from the Blue data-source specification, with the reason for each. Anyone porting a caller should read this first.

## Relationship to the data-source specification

The specification referred to throughout this file is the Blue team's internal data-source design document. It is not shipped with this package and is not quoted here beyond what each difference below needs, so the differences are stated in full rather than by reference.

**The source inherits from `DataSource`, as the document specifies.** `LlmSource` extends `blue_data.source.source.DataSource` directly, and `blue-data>=0.1.0` is a declared core dependency alongside `tenacity>=9.0.0`. The `[blue-data]` extra that used to gate the base class is gone. An earlier version of this package declared no dependency on the data layer and matched the query surface by shape instead; anything you have read describing this package as standalone, or the data layer as optional to it, belongs to that version and is no longer true.

Base-class order is load-bearing rather than cosmetic. `DataSource` is a plain class, not an abstract one. Most of its methods return an empty result, so one left unoverridden answers nothing rather than failing: `fetch_databases` would return an empty list and `execute_query` would return no records without a model ever being contacted, silently. `LlmSource` is declared with `DataSource` as its base so its own implementations come first in the method resolution order, and a test asserts that every method on the shared surface still resolves to this class.

Be precise about what the dependency buys. **Registering an already-constructed instance is the route**: `register_source` stores the object under its name and records its class alongside `name` and `properties`. `connect_source` then returns that live instance while it is present, and reconstructs an equivalent source from the recorded class once it is not, so the registration outlives the object that made it. Dispatch by protocol name is a legacy path for older records and is not how this source is reached; inheriting the base class does not add a protocol arm and does not need to.

So the supported integration today is: build the source, then hand the instance to `register_source`. Protocol-driven construction needs the upstream addition first.

`blue_data_llm_source.compat.blue_data.BlueDataLlmSource` is an alias for `LlmSource`, kept so an import written against the earlier optional adapter keeps working. It is not a subclass: there is nothing left for one to add now that the core carries the inheritance, and a second class would be a second method resolution order to get wrong for no behaviour of its own. New code should import `LlmSource`.

**What the dependency costs.** `blue-data` brings `pandas`, `numpy`, and `jsonpath-ng` with it, so installing this package pulls in a scientific stack it does not itself use. That is the figure to weigh, and it is written here so that whoever weighs it does not have to resolve the tree to find out. What the dependency does not bring is the orchestration layer above the data layer: nothing here imports `blue` or `blue_data_ops`, and a test asserts it, because a data source that reaches into the runtime calling it cannot be used anywhere else.

**Errors are raised, not returned.** The document says that on an exception the source should return the exception only. This library raises a typed error from the `LlmSourceError` hierarchy. A raised error is the right contract for a library, since a caller that ignores a returned error object gets a silent wrong answer, while an operator boundary that needs an error value can convert one. Anyone relying on the documented return-the-exception behaviour needs a `try`/`except` at the call site.

One classification is worth stating because it is easy to guess wrong. A missing or invalid provider credential is not a `ConfigError`. This library never reads a credential, so it cannot find one missing; the provider SDK reports it as a failed call, which becomes a `TransportError` and, through the CLI, exit code 5. `ConfigError` covers the configuration this package does check: an unknown override, an invalid or unknown ceiling, a ceiling the resolved client cannot hold, and a missing optional extra.

## Deviations from the monolith implementation

**The protocol is `llm`, not `openai`.** The design document specifies protocol `llm` with variant `openai`, matching how `sql` covers both `postgres` and `mysql`. The monolith registers under `openai`, which names a vendor where a family was specified. A registry entry pointing at the old protocol string needs updating.

**A `variant` property exists.** It defaults to `openai` and is settable. The monolith has no such property.

**Code fences are stripped by matching the fence.** The monolith removes every occurrence of the substring `json` from the response, which corrupts any returned value containing that substring. This library matches an actual surrounding fence and leaves the content alone.

**Template substitution is single-pass and does not interpret user text.** The monolith applies `Template.safe_substitute` and then Jinja2, repeatedly, until the string stops changing. A query containing `${...}` or `{{...}}` is therefore expanded as a template. Here the prompt has a fixed set of named fields and user text is inserted as a value, never re-read.

**Calls are bounded.** The monolith has no timeout, no retry, and no ceiling. This library retries transport failures with exponential backoff and enforces four limits: rows, time, cost, and call count. The time limit bounds admission and waiting rather than the whole run; [what it bounds](README.md#what-the-time-ceiling-actually-bounds) is stated exactly. Time, calls, and cost are all claimed before each provider attempt, and rows are capped once the records are parsed. When a limit stops a run, `meta.stopped_by` names it and the records already collected are returned rather than discarded. Every `limits.*` name is checked against a closed set and every value against its type, so a misspelled or malformed ceiling raises `ConfigError` rather than being accepted and ignored.

**The cost claim is an upper bound, or the ceiling is refused.** A call's price is not known until it returns, so `limits.max_cost` is claimed against the prompt's length in UTF-8 bytes plus a framing allowance at the model's published input rate, plus the whole `llm.max_tokens` allowance at its output rate, reconciled against the real figure once the call returns. Counting bytes rather than dividing by an average is what makes it a bound: a byte-pair tokenizer merges byte sequences, so every token it emits consumes at least one byte of the encoded prompt, while an average is exceeded by dense text. Counting characters would not have been a bound even though it reads like one, since a tokenizer splits a character whose encoding it has no merge for. Where no bound can be established the ceiling raises `ConfigError` instead of resting on a guess: when the model carries no published price and none was supplied, and when `llm.max_tokens` is not a finite positive number.

The number to size a ceiling against is the floor of that bound, which is the output allowance alone and does not depend on the prompt. With the shipped defaults of `gpt-4o` and 4096 output tokens it is about $0.041, so a smaller `limits.max_cost` refuses every call before making one. Lower `llm.max_tokens` rather than raising the ceiling.

**A caller can ask what a request would cost before running it.** `LlmSource.estimate(query, attrs, context, properties)` builds the prompt this source would actually send, bounds it the way a reservation does, and returns an `Estimate` without contacting anything. The monolith has no equivalent, so a caller that wanted to know had to run the request and read the invoice. Because it is the same bound the reservation claims, an estimate and the ceiling that enforces it cannot disagree: a request that estimates inside a ceiling is not refused when it runs. It is also reachable through the query surface as the op `LLM.ESTIMATE`, which returns the estimate as a one-record list, since a caller reaching this source through the registry is exactly the caller that has to size work before committing to it. A model this package cannot price comes back with `bounded` false and a `reason`, rather than raising, because asking what a request might cost is a reasonable question even where the answer is unavailable.

**A client declares which ceilings it can hold, per axis.** `types.BudgetAwareClient` requires one method, `budget_capabilities() -> frozenset[str]`, returning names from `types.Capability`: `CALLS`, `ROWS`, `SECONDS`, `COST`, `ESTIMATE`, or `ALL`, which is all five. **`ESTIMATE` is not a ceiling and `ALL` includes it**, so declaring `ALL` commits a client to two further things: that it implements `bound_for_attempt(prompt, properties) -> float` returning a true upper bound on one provider attempt, and that one call makes at most `budget.effective_retries() + 1` provider attempts. `estimate` publishes a whole-fetch bound by accumulating the per-attempt figure once per permitted attempt, so a client with its own retry or fallback policy that ignores the allowance can spend past a figure a caller sized a ceiling from. A client that cannot promise both declares the four ceiling axes it can hold and omits `ESTIMATE`; `estimate` then reports `bounded=False` with a reason, which is the honest answer. A client that declares an axis receives the run's budget under the `budget` property on every call and is expected to reserve against it per provider attempt and resolve each reservation. Every configured ceiling on an axis the client did not declare is refused with a `ConfigError` at the first fetch, because a ceiling that is not holding anything is worse than no ceiling: the caller believes it.

A method rather than an attribute is deliberate. An earlier version accepted any object carrying an attribute named `budget`, which a client holding `budget = None` satisfied while making unbounded calls under a configured ceiling. Per axis rather than as one flag is equally deliberate: `DefaultLlmClient` declares `Capability.ALL` because it makes the provider call itself, while `FunctionClient`, which wraps a callable passed as `llm_fn`, declares rows and nothing else. It can prove it invoked that callable once, and one invocation is not one provider call: the callable may answer from its own memory, contact a provider once, or fan out to several. So `limits.max_calls`, `limits.max_cost`, and `limits.max_seconds` over an `llm_fn` are **refused** where a previous version settled them at a cost of zero and appeared to hold them.

Anyone porting a caller that injects its own client should implement `budget_capabilities`, claim against the budget it receives, and append this call's `Usage` to the list arriving under the `usage_sink` property, which is where the fetch reads its token counts and model name from. A client that declares nothing still works; it is refused the three provider-level ceilings, and `limits.max_rows` needs nothing from it.

**A ceiling is an input to the query.** `execute_query` and `execute_query_nl` both take `optional_properties`, and a `limits.*` key placed there binds that call and no other: the properties are merged over the instance's for the duration of the request and are not written back. That is how a caller reaching this source through the query surface bounds a request, and it is the route to reach for first, because it needs nothing beyond the arguments the surface already takes.

**A caller can also own the budget.** Limits configured on the source, or handed to one call through `optional_properties`, bound that fetch. `fetch` and `afetch` additionally accept `budget=`, a `Budget` the caller holds, from which each fetch derives a child that spends against what the caller has left. That is the second route, and it is the one to use when the ceiling is a total across several requests rather than a bound on any one of them.

**One prompt, in one module.** The monolith holds two copies with divergent wording and different variable names, one on the source and one on the `nl2llm` operator. This library has one, in `prompts/`.

**Unknown configuration keys are rejected.** An unrecognised `llm.*` key raises `ConfigError` naming the accepted set. The value of failing loudly here is specific: an accepted-and-ignored setting means recorded configuration no longer describes what ran.

**Keys that collide are reported, not resolved.** The monolith selects requested columns and lets a later key overwrite an earlier one. Here the first key to answer a requested attribute keeps it, and the second is reported in `meta.key_collisions` with the value it carried, because which spelling the model meant is not knowable and letting the later one win makes the answer depend on JSON key order. Two *requested* attributes whose fuzzy forms coincide are a third case and are not refused: the fuzzy index drops the entry it cannot separate, exact keys still match, and a key that only matches fuzzily is reported unmapped. Two occurrences of the *identical* key inside one object are a fourth case and raise `ParseError`, at any nesting depth: two distinguishable spellings leave something to report, while one key repeated leaves nothing to tell the values apart by, and Python's decoder would otherwise keep the last and leave no trace of the first. Two *requested* attributes that normalise to the same key raise `QueryError` instead, including two identical spellings, since no returned value could be assigned to either without guessing.

**An empty result carries one outcome, decided by one rule.** `source.decide_outcome` is public and ordered: any `stopped_by` wins, giving `truncated` when the row cap fired and records remain and `stopped_by_limit` otherwise; then records present is `ok`, nothing from the model is `model_returned_none`, and records that reduction removed is `filtered_to_empty`. A caller porting from a version that read `stopped_by_limit` as only a pre-provider refusal should note that a run which produced records and was found over its cost ceiling during settlement reports it too.

**The virtual entity is not vendor-named.** The monolith synthesises `openai_entity` and `openai_entity_attribute`. This library uses `llm_entity` and `llm_entity_attribute`, consistent with the protocol being the family.

**A fresh source is not constructed per call.** The monolith builds a new source object on every registry call. This library holds no connection and constructs a client per fetch, so a single instance is reusable.

## Behaviour kept deliberately

Both attribute forms work: a plain list of names, which is what the design document specifies, and a list of `{name, type}` dicts, which is what the operator uses. Types are used for verification when present.

`context` is free text that may clarify what an attribute name means, matching the documented use rather than only carrying background information.

An empty or whitespace query never reaches the model. Both the monolith and this library return an empty list rather than raising, and this library additionally reports `outcome: empty_query` in the result metadata, so a caller can tell a skipped request apart from a model that found nothing.

The virtual hierarchy of one database, one collection, and one entity with one text attribute is preserved so a registry sync has something to walk.

## Not carried over

The `nl2llm` operator and the `NL2LLM` agent are not part of this library. Per the layer's own design, natural-language querying of a source is provided by a per-source `NL2Q*` operator, which belongs with the operator library. This package is the source that such an operator calls.
