# LlmSource — Overview

## Objective

Every source in a data layer answers a question by reading something: a table, a document, a graph, a vector index. A language model answers a large class of questions without reading anything, from what it already encodes. Which countries belong to a trade bloc, which companies listed in a given year, what the standard sizes of a shipping container are. That knowledge is real and it is queryable, but a data layer can only reach it as free text, which means a planner cannot join against it, an operator cannot type it, and nothing downstream can tell a complete answer from a partial one. Making that knowledge available as records, under the same query surface every other source presents, is what turns it from something an agent quotes into something a pipeline can use.

## What LlmSource Does

blue-data-llm-source presents a language model as a data source. Specifically, it enables a system to:

- Fetch structured records from a model's own knowledge: a natural language request, an optional attribute list, and optional context in; a list of records out. There is no retrieval step and no backing store.
- Align the keys a model returns onto the attributes the caller asked for, coerce values to their declared types where the coercion is unambiguous, and drop exact duplicates.
- Report what could not be placed rather than discarding it, so a caller sees the keys the model chose, the keys that were remapped, the keys that had no home, the values that did not fit the type they were declared as, and the value that was ignored when two returned keys answered the same attribute.
- Bound every run on four axes at once, being row count, elapsed time, API cost, and provider call count. Calls, time, and cost are claimed before the provider is contacted rather than recorded after the fact, cost as a genuine upper bound that is reconciled against the real price once the call returns. A cost ceiling whose bound cannot be established, because the model has no published price or its output is uncapped, is refused rather than claimed against a guess. Rows are admitted once the records are in hand, which is the first moment their count exists. The time axis bounds admission and cooperative waiting rather than the whole run; [what it bounds](../../lib/README.md#what-the-time-ceiling-actually-bounds) lists the exclusions.
- Take the ceiling as part of the request. `execute_query` and `execute_query_nl` accept `optional_properties`, and a `limits.*` key placed there binds that call and does not leak into the next, so a caller bounds a request with the arguments the surface already takes rather than by reconfiguring the source.
- Take a budget from the caller when one is offered, so a session or a planner can bound a whole unit of work rather than each request separately, and derive a child from it per fetch so that no request can spend more than the caller has left. That is the second route, for a total across calls; the first bounds one call.
- Say what a request would cost before it is run. `estimate` builds the prompt the source would actually send, bounds it, contacts nothing, and returns the same figure the reservation would claim, so a planner can size a fan-out and an operator can check a request against a ceiling without spending anything to learn the answer. A model the package cannot price is reported as unbounded with a reason rather than raising.
- Report what a run cost, including the model used, the number of calls, prompt and completion tokens, spend, elapsed time, cache hits, and which limit stopped it.
- Say why a result is empty. An empty result is an answer here, and it carries a reason from a closed vocabulary, so a caller can tell an empty request from a model that knows nothing, a result filtered away, and a run a ceiling stopped.
- Present the data layer's source query surface, `execute_query` and `execute_query_nl`, under protocol `llm` and variant `openai`, so the source can be registered and queried alongside SQL, document, graph, and vector sources. It inherits `blue_data.source.source.DataSource` to do so, which is what makes it a source of that layer by type rather than by resemblance.
- Accept an injected model client, so the library holds no credentials, carries no provider SDK in its required dependencies, and runs offline under test. A client declares which axes it can be held to, is handed the run's budget on every call, and is refused each configured ceiling on an axis it did not declare, rather than reported as bounded by a number that is not holding anything.

## What It Depends On

The package takes two runtime dependencies, `blue-data>=0.1.0` and `tenacity>=9.0.0`. `blue-data` supplies the `DataSource` base class, and taking it as a declared dependency rather than matching its shape is a deliberate widening of an earlier position: every other source in the layer inherits that class, so a divergence from the surface becomes a type error instead of a drift discovered by whoever integrates against it. The cost is `pandas`, `numpy`, and `jsonpath-ng`, which `blue-data` brings along, so the install pulls in a scientific stack this package does not itself use.

The boundary the dependency does not cross is the one above the data layer. Nothing here imports `blue` or `blue_data_ops`, and a test asserts it, because a source that reaches into the runtime calling it cannot be used outside that runtime. Depending on the data layer is not the same as depending on the orchestrator that queries it.

Inheritance also does not make the source reachable by protocol name. The integration route is to build the source and register the instance. `connect_source` then returns that live instance by name, and reconstructs an equivalent one from the recorded class path if the live entry is gone, so a registration survives beyond the object that made it. That is an upstream change rather than something this package can supply, and it is the same route the source had before the dependency was taken.

## Design Philosophy

LlmSource treats the model as a source whose failure mode is silence rather than error. A SQL source that returns forty rows returned forty rows, and a source that cannot answer raises. A model asked for two hundred records returns forty, stops at a plausible place, reports nothing wrong, and may invent the forty-first. The call itself is short; the engineering is in the surrounding accounting, which is why the design puts its weight on the boundaries rather than the middle. Every value the caller declared is checked against the type it was given and reported when it does not fit, every key the model volunteered is either mapped or named in the report, every provider attempt is reserved against a budget before it is made, and every run returns a record of what it spent and why its result looks as it does alongside the records it produced. Where the source cannot establish something, it says so instead of implying it: this release verifies that a record matches the shape it was asked for, and it does not verify that a claim is true.
