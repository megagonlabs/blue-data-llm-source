# Changelog

Notable changes by release. Prompt changes are listed explicitly because they can alter results without changing a public API.

## 1.0.0 — current

Earlier internal versions were numbered 1.0.0 to 2.2.1. They are listed here as 0.1.0.0 to 0.2.2.1 so they read in order below 1.0.0, and each heading gives the original number. None was published to a package index. Installed copies still report their original numbers: pip ranks an installed 0.1.1.0 to 0.2.2.1 (1.1.0 to 2.2.1) above 1.0.0, so an ordinary upgrade does not select this release, and an installed 0.1.0.0 also reports 1.0.0. See [installing exact built wheels](docs/installation.md#installing-exact-built-wheels).

- **Provider diagnostics.** The default client suppresses LiteLLM INFO/DEBUG messages before importing the provider and disables its error help banner. Existing handlers and stricter logging levels are retained.
- **Native operations.** JSON-encoded operation objects use the same dispatcher as operation dicts. `LLM.MODELS` and `LLM.ESTIMATE` remain offline. Names are case-sensitive, and an invalid tag raises `QueryError` before a fetch. Other query strings keep their natural-language meaning.
- **Partition estimates.** Non-flat results report `split_coverage_short` for accepted child estimates below the parent's lower estimate, and `observed_coverage_short` for complete identities below the root lower estimate before row capping. These are estimate-based warnings; execution outcomes and model prompts are unchanged.
- **CLI and examples.** Natural-language estimates use the configured-rate wording shown in the docs. The JSON ceiling examples include conditional accounting and provenance fields. The WikiTabGen demo reserves a cost, call and time share for each selected mode under the shared total budget. The LangGraph MCP demo uses `create_agent` and carries its conversation history between tasks.
- **Dates.** An `NN-NN-YYYY` date converts day-first only when the first part is above 12 or both parts are equal (`03-03-2026` becomes `2026-03-03`). Any other `NN-NN-YYYY` value is kept as given and reported in `meta.type_mismatches`.
- **Planner types.** The planner accepts the ten documented type spellings (`string`, `str`, `text`, `integer`, `int`, `number`, `float`, `boolean`, `bool`, `date`). A caller-declared custom type such as `money` keeps the planner's schema and key and is listed in `meta.unchecked_types`. An unsupported inferred type still makes the schema unusable, so the caller schema is used.
- **Limits.** A per-call `limits.*` setting can only tighten a configured ceiling, and `max_records` is clamped to `limits.max_rows`. While the client or source sets `limits.max_cost`, a per-call `llm.price_per_input_token` or `llm.price_per_output_token` is refused, and a per-call `llm.model` does not inherit the configured rates. See [`lib/COMPATIBILITY.md`](lib/COMPATIBILITY.md).
- **Shared source surface.** `optional_properties["commit"]` is accepted and ignored, `metadata` is tolerated, `get_sample` returns `None` and is now advertised by `get_nl_tools` (five tools instead of four), and the query and creation methods take `read_only` and `overwrite` parameters.
- **Synchronous calls inside a running event loop.** `fetch`, `execute_query` and `execute_query_nl` now block the calling thread and run on a worker thread instead of raising `ConfigError`. Under `asyncio.run` on Python 3.11 and later, the first Ctrl-C cancels the in-flight fetch when the synchronous call runs in the runner's main task. A call in another task observes cancellation only if that task receives the request. In a plain event-loop callback, that signal cancels the runner's main task while the fetch continues; a second Ctrl-C interrupts the waiting thread. Schedule and await `afetch` in a task for cancellable asynchronous work. Once the bridge receives an interrupt or task-cancellation request, it raises as soon as the fetch stops, or after five seconds if the client ignores cancellation; that work then finishes in the background. A client that needs the caller's loop should use `afetch`.
- **CLI configuration.** The CLI uses the shared `blue_data.utils.config` engine. Boolean settings accept `y` and `n`, and environment values are stripped. A blank value edited into a profile by hand no longer blocks the `profile` commands, so it can be repaired; data, model and metadata commands still refuse it.
- **MCP.** A blank `BLUE_DATA_LLM_SOURCE_LIMIT_*` variable fails the call instead of being read as unset. Every `mcp` requirement is `mcp>=1.28.1,<2`. The CLI and MCP packages require `blue-data-llm-source[llm]==1.0.0`, the core requires `blue-data>=1.0.0,<2`, and the CLI also requires `blue-data==1.0.0`.
- **Python support.** All packages support Python 3.12 and 3.13 (`>=3.12,<3.14`). The obsolete compatibility-wheel builders, constraints and Python 3.15 installer branch are removed; the [installation anchor](docs/installation.md#python-315-installation) explains that 3.15 is unsupported.
- **Documentation and license files.** Configured model choice, single-process asynchronous task execution, and key normalization with keyed deduplication are described as they behave: there is no model router, remote executor or general entity resolution. Setup uses `source .venv/bin/activate` and names Python 3.12 as the tested version. The repository adds `NOTICE` files, a code of conduct and license disclosures.

**Prompt changes**

- **`SCHEMA`.** It lists `date` among the inferred types, states that declared aliases (`int`, `float`, `bool`, `str`, `text`) stay unchanged, and tells the model to keep caller-supplied primary keys and, when none were supplied, to infer a key only when defensible. An empty `primary_keys` list means no key was supplied.
- **`BOOTSTRAP`.** It gains the same two key sentences.

## 0.2.2.1 — unreleased (as 2.2.1)

Version 0.2.2.1 protects diagnostic output and local cache files, tightens package publication scripts, and keeps inherited range filters intact during query planning. It does not change model prompts or the default settings introduced in 0.2.2.0.

- **CLI JSON mode reports argument errors as JSON.** On a command with `--format`, an explicit `--format json` or an available `BLUE_DATA_CLI_FORMAT=json` default writes a redacted `{"error": {"code": "USAGE", "message": ...}}` object to standard output for parse failures. Exit 2 and the coded standard error line remain. Startup errors also use an already known JSON default when profile resolution fails. Commands without `--format` continue to report these errors only on standard error.
- **CLI commands refuse missing selected profiles.** Data, model, and metadata commands report `PROFILE` with exit 4 when a stored selection or implicit `default` is absent, before profile settings or provider calls are used. Profile commands remain available to repair the selection or create a profile.
- **CLI and MCP diagnostics mask credential-shaped text.** The masking covers metadata keys and values, including values from records discarded during alignment or deduplication. Returned records and direct Python results retain their original values. Malformed CLI profile errors no longer quote profile-file contents, and provider output cannot write into the CLI's standard output.
- **MCP errors use fixed messages for library and provider failures.** The server retains known error kinds without returning underlying exception text to callers.
- **On-disk caches use private directories.** The built-in `diskcache` backend and `FileCache` create directories with owner-only access and refuse existing directories with broader permissions on POSIX systems. An existing `.llm_cache` may need `chmod 700 .llm_cache` before caching can resume. `FileCache.clear()` removes only entries written by that instance.
- **Partitioning preserves inherited numeric ranges.** A proposed split or entity enumeration on a range-constrained key keeps the parent task when the proposed children cannot establish coverage of that range.
- **Publish scripts require an explicit HTTPS repository URL.** All three refuse a missing URL or one with embedded userinfo.
- **The library, CLI, and MCP server reported version 2.2.1.** The CLI and MCP server required `blue-data-llm-source[llm]>=2.2.1`.
- **Correction to the 0.1.2.0 `LLM.ESTIMATE` note.** That entry describes the model as asked once. The estimate actually prices a flat fetch, including its permitted retries. `max_records` limits returned rows but is not a provider-call or cost ceiling; planned fetches may make several calls.
- **Correction to the 0.2.1.0 cost note.** Under a cost ceiling, a contacted attempt retains at least its reservation. A usage-derived bound may increase that charge but does not replace it with a lower figure. Two earlier demo captures are labeled as historical because their displayed costs do not reflect this settlement rule.
- **Pre-call cost bounds include known worst-case billing factors.** For listed models, admission now includes the cache-write and long-context multipliers wherever the model entry supplies them, even for a short prompt. This matches the conservative ledger charge after provider contact. The default `gpt-6-luna` output-only floor at 25,000 tokens is about $0.020625. Estimates and ceilings use the same calculation; the figure depends on the package or configured rates and the provider honoring the token allowance.

## 0.2.2.0 — released (as 2.2.0)

Version 0.2.2.0 adds an opt-in setting, `plan.split_policy="evidence"`, that lets a `partitioned` request answer from one call when one call is enough and split only when there is evidence it is not. It also adds five experimental plan settings that change how a split request asks each part. Every new setting defaults to the 0.2.1.0 behavior. At the defaults a request sends the same prompts and returns the same records as 0.2.1.0; its result metadata gains one field, `filter_contradictions`.

**The evidence-gated split.** Under `plan.split_policy="evidence"` the root of a partitioned plan is asked once before any split is proposed. That one ask, called the probe, is the whole request sent as a single leaf. The plan splits only when the probe's answer was cut off, failed, or holds fewer than half the keys a row estimate above `plan.split_threshold_rows` (default 120) expects. When the plan splits, it merges the probe's records with the children's records. This policy is opt-in and does not establish that the answer is complete. The shortfall rule applies only above the threshold, so a smaller answer can be accepted even when its row estimate is higher.

**Experimental settings.** `plan.leaf_prompt`, `plan.child_wording`, `plan.filter_enforcement`, `plan.range_filters` and `plan.partition_guardrails` are experimental and off by default. None adds a call or changes a published call bound. Check the records and diagnostics when selecting a different leaf prompt or filter policy; these settings do not establish completeness.

**Upgrading from 0.2.1.0.** Nothing changes for a caller that sets none of the new settings, apart from these:

- **Result metadata carries `filter_contradictions`.** It is always present: on `ExecMeta`, in `FetchResult.to_dict()`, in `meta_view`, and in the CLI and MCP result `meta`. It counts records whose value in a split column contradicts the filter of the leaf that returned them. It is `0` for a `flat` request and can be non-zero in the other modes at the defaults, where such records are counted and kept, as 0.2.1.0 kept them. A consumer that checks the exact set of `meta` keys sees one more.
- **`ExecMeta` has two new fields, `split_decision` and `filter_contradictions`, ahead of `observed_keys`.** A caller that builds `ExecMeta` positionally past `repaired_numbers` needs keyword arguments.
- **New serialized versions appear only under the new settings.** This matters only to a caller that stores fetch plans or leaf tasks, or sends them between processes, across 0.2.1.0 and 0.2.2.0; a caller that only calls `fetch()` is unaffected. At the defaults a fetch plan is still written as `serialization_version` 1 and every leaf task keeps its 0.2.1.0 wire version. A plan carrying a range filter is written as version 2, a task built for `keyed-leaf-fetch-2` travels on wire version 5, and a task seeded with the probe's keys under `plan.split_policy="evidence"` travels on wire version 6 with the default leaf contract, or on wire version 5 with `keyed-leaf-fetch-2`. A 0.2.1.0 reader refuses all three by their version.
- **The CLI and MCP server required `blue-data-llm-source[llm]>=2.2.0`**, because they pass the new settings to the library.

**Prompt changes**

- **New leaf contract `keyed-leaf-fetch-2`, selected by `plan.leaf_prompt`.** It adds two requirements to `keyed-leaf-fetch-1`: return every record that matches the request within its scope and satisfies the column filters, rather than a sample, and return `[]` only when no record matches the column filters within the request scope. It also splits the leaf's constraints. A constraint that partitioning introduced and that names one schema column, matched without regard to case, is sent as a column filter every record must satisfy. Everything else is request scope that records need not carry: every constraint the analysis step or the caller set for the whole request, even one whose key matches a column, and child-specific slices on keys that name no column, such as a decade. The row estimate is sent as one sentence ("Expected count: about 30 matching records ... This is a rough estimate, not a limit") in place of the estimate object, and is still omitted when `plan.expose_estimate` is false. It applies to the root, single-leaf and child prompts. `keyed-leaf-fetch-1` is unchanged and remains the default.
- **New partition contract `partition-2`, selected by `plan.partition_guardrails`.** It adds rules against identifier and continuous-measurement keys, placeholder values and catch-all values, and suggests a value count from the slice's own row estimate and `plan.target_rows_per_leaf`. The proposal prompt without the setting, now named `partition-1`, is unchanged.
- **Child retrieval wording under `plan.child_wording="canonical"`.** Each partitioned child is asked with the root request plus its own filters, such as `…, restricted to the slice the column filters define ("year" from 1946 to 1952); the column filters are authoritative`, in place of its parent's wording. The wording is built from the validated filters and never by a model; it names the column filters only, by the same rule, field names and values are quoted as JSON literals, and the wording defers to the structured filters. A split on a key that is no schema column stays out of the wording and reaches the leaf as per-child request scope.
- **Range filters in leaf and planning prompts under `plan.range_filters`.** A range filter is shown as `{"kind": "range", "min": 1946, "max": 1952}`.

**Added**

- **`plan.leaf_prompt`**, `keyed-leaf-fetch-1` (default) or `keyed-leaf-fetch-2`, for non-flat modes. Tasks built for the new contract travel on leaf-task wire version 5, which admits only that contract; both contracts execute. The local executor refuses a result answered under the other contract: a wire version 5 task needs a wire version 5 result, and an older task's result may not be on wire version 5.
- **`plan.child_wording`**, `parent` (default) or `canonical`, in `partitioned` mode.
- **`meta.filter_contradictions`**, always present: the records whose checkable filter column contradicts the filter of the leaf that returned them, counted before reduction. A filter is checked only on a declared attribute of a type the key normalizer reads, and only when that type can read both values, so a zero means none was observed.
- **`plan.filter_enforcement`**, `flag` (default) keeps those records and `drop` removes them at the leaf, before reduction merges them into anything. Both count them.
- **`Range` and `plan.range_filters`** (default `False`). In `partitioned` mode, a proposal written as integer spans on a column declared `int` or `integer` becomes inclusive `Range` filters instead of exact text. Overlapping or reversed spans refuse the proposal with the reason. A range holds only integer values, so `2.5` is not in `Range(1, 3)`, and a leaf task may carry one only on an attribute declared `int` or `integer`. It requires `plan.leaf_prompt="keyed-leaf-fetch-2"`, since only wire version 5 carries a range.
- **Fetch plan serialization version 2.** A plan carrying any `Range` constraint is written as `serialization_version` 2, which a 0.2.1.0 reader refuses by its version. A plan without ranges is still written as version 1, unchanged, and the reader accepts both.
- **`plan.partition_guardrails`** (default `False`). Besides the `partition-2` prompt, it refuses a model-proposed key declared `int`, `integer`, `float` or `number` unless its values are integers or integer spans covering at most 1,000 integers. The reason is reported as a `guard_collapsed` gap.
- **`plan.split_policy`**, `always` (default) or `evidence`, and **`plan.split_threshold_rows`** (default `120`), in `partitioned` mode. Under `evidence` the root leaf is asked once, with no continuation, before any split is proposed. The plan splits only when the provider says that answer hit its output allowance, the answer ended mid-document and only its complete records could be read, the probe failed outright (reported as a gap such as `probe_failed: RuntimeError`, which names the exception type and none of the provider's text), or it holds fewer than half the keys an estimate above the threshold expects; otherwise it is the result, with no proposal call. The probe is a single ask even when `plan.max_continuations` is set, and one that meets `plan.exact_rows` is accepted unless its answer was cut; a target of zero asks nothing and reports no `split_decision`. On a split its records are merged with the children's under the origin `root`, and each child's first prompt lists the complete keys the probe already holds, bounded by `plan.max_excluded_keys` and `plan.max_exclusion_bytes`; a probe record without a complete key is not listed. The probe counts as one logical call in every accessor in `planning.bounds`, which gain a `split_policy` argument and a new `probe_calls`.
- **`meta.split_decision`**, present only when a probe ran, in `meta_view` and in `FetchResult.to_dict()`: `probe_accepted`, `probe_split_length`, `probe_split_incomplete`, `probe_split_shortfall` or `probe_split_failed`.
- **Leaf-task wire version 6.** A `keyed-leaf-fetch-1` task seeded with the probe's keys carries `held_exclusions` and `held_total` on wire version 6; wire version 5 carries the same two fields. An unseeded task keeps its 0.2.1.0 wire version and payload.
- **CLI and MCP.** `--plan-split-policy` and `--plan-split-threshold-rows`, and the matching `plan.*` arguments on `llmdb_query`.
- **CLI and MCP.** `--plan-leaf-prompt`, `--plan-child-wording`, `--plan-filter-enforcement`, `--plan-range-filters` and `--plan-partition-guardrails`, and the matching `plan.*` arguments on `llmdb_query`. The standard planning controls shared by Python, the CLI and MCP go from 14 to 19, and with the split settings to 21.

**Changed**

- **The CLI and MCP result `meta` carries `filter_contradictions`**, `0` unless a leaf returned a contradicting record.
- **The version was 2.2.0 in all three packages**, and the CLI and MCP server required `blue-data-llm-source[llm]>=2.2.0`.
- **A non-default switch is refused in a mode that cannot use it.** `plan.leaf_prompt="keyed-leaf-fetch-2"` and `plan.filter_enforcement="drop"` need a non-flat mode; `plan.child_wording="canonical"`, `plan.range_filters` and `plan.partition_guardrails` need `partitioned`.

## 0.2.1.0 — released (as 2.1.0)

Version 0.2.1.0 updates the library, CLI, and MCP server to send OpenAI's current GPT models, from GPT-4o to GPT-6, the request arguments each requires and to apply a cost ceiling to each. It also fixes cost accounting that reported an unpriced call as free and makes the MCP server read the deployment settings documented for it.

**Upgrading from 0.2.0.0.** These behavior changes can alter what an existing caller gets. Each item gives the setting that keeps the 0.2.0.0 behavior where one exists.

- **The default model is `gpt-6-luna`, not `gpt-4o`.** Set `llm.model=gpt-4o`; on the CLI, `blue-llmdb model select gpt-4o`, and on the MCP server, `BLUE_DATA_LLM_MODEL=gpt-4o`.
- **Planning caps rise from 4 partitions and 24 leaves to 20 and 100.** Set `plan.max_partitions=4` and `plan.max_leaves=24`, or `--plan-partitions 4 --plan-leaves 24`. A `flat` request, the default, is unaffected.
- **`LlmSource.properties` no longer lists the package defaults.** Read a model's defaults with `published_defaults(model)`, and the model that answered from `meta.model`.
- **CLI profile files readable or writable by group or others are refused.** Run `chmod 600 ~/.blue-llmdb/.profiles ~/.blue-llmdb/.selected.profile`.
- **The `claude-*` price rows are removed.** A cost ceiling on one of those names needs `llm.price_per_input_token` and `llm.price_per_output_token`.
- **The MCP server reads settings from its environment,** including operator ceilings: `BLUE_DATA_LLM_MODEL`, the `BLUE_DATA_LLM_SOURCE_*` request settings, and `BLUE_DATA_LLM_SOURCE_LIMIT_COST`, `_LIMIT_CALLS` and `_LIMIT_SECONDS`. Leave them unset in the client's server config to run as 0.2.0.0 did, apart from the default model above. [MCP configuration](docs/mcp.md#configuration) lists them.

**Added**

- **One model table for requests and prices.** `llm/models.py` records each supported OpenAI model's request settings and rates, so the request a call sends and the rates its ceiling is bounded against come from the same entry. The [supported models](lib/README.md#supported-models) table lists them.
- **`openai/<name>` reads the same entry as `<name>`.** `openai/gpt-6-sol` is requested and bounded as `gpt-6-sol`. The name sent to the provider is unchanged.
- **Reasoning effort.** `llm.reasoning_effort`, `--reasoning-effort` and `BLUE_DATA_LLM_SOURCE_REASONING_EFFORT` accept `none`, `minimal`, `low`, `medium`, `high`, `xhigh` or `max`, and each model accepts the subset its table entry lists; `minimal` is for the GPT-5 family, the one family that offers it. The client sends each model's own output-token argument and refuses an incompatible effort and temperature before any provider call.
- **`published_defaults`.** A new export returns one model's table entry, or `None` for a model the table does not carry. `blue-llmdb model inspect` adds it as `published_defaults.*` rows, and `llmdb_inspect_model` as a `published_defaults` object. Both label it as the model's published defaults, since a deployment's own settings win over them.
- **The MCP server reads its deployment settings from the environment.** `BLUE_DATA_LLM_MODEL` and nine `BLUE_DATA_LLM_SOURCE_*` variables, under the CLI's names, set the `llm.*` settings on every call, and a malformed value fails that call with a `ConfigError` naming the variable but not the value. [MCP configuration](docs/mcp.md#configuration) lists them.

- **Operator ceilings for the MCP server.** `BLUE_DATA_LLM_SOURCE_LIMIT_COST`, `_LIMIT_CALLS` and `_LIMIT_SECONDS`, the CLI profile's names, set `limits.max_cost`, `limits.max_calls` and `limits.max_seconds` for every call. A call's own `limits.*` argument applies only where it is lower, so an agent can tighten a ceiling but never raise or remove it, and `llmdb_estimate` sees the ceiling that applies. A malformed value fails the call with a `ConfigError` naming the variable, not the value. Before this, any agent call that set no ceiling ran unbounded.
- **`Estimate.attempts_within_ceiling`.** With a cost ceiling, `estimate` reports how many of `max_attempts` fit under it, counted the way the ledger admits them; `0` means the first attempt would be refused. `blue-llmdb data estimate --limit-cost` says "At this ceiling N of M attempts fit", or names the first attempt's figure and the `--max-tokens` remedy, and `llmdb_estimate` carries the field.

**Changed**

- **`limits.max_retries` accepts at most 9,999**, so one call makes at most 10,000 attempts. A larger value, including one too large for a float, is refused with a `ConfigError` naming the field and the maximum before any provider contact, in the library, `--max-retries` and `BLUE_DATA_LLM_SOURCE_MAX_RETRIES`. The MCP server takes no retry setting.
- **A run the cost ceiling refuses outright says what to change.** When one attempt's bound is above the whole ceiling, the refusal names that figure, the ceiling, and `llm.max_tokens` as the setting that lowers it, in the stop message and in the leaf's gap. `blue-llmdb data query` adds the `--max-tokens` and `--limit-cost` remedy to its `stopped by: max_cost` line.
- **`LlmSource.properties` holds only the connection and what the caller set.** Package defaults, the model, output allowance, temperature and streaming flag, no longer appear there. `published_defaults(model)` returns a table model's defaults, and a result's `meta.model` names the model that answered.
- **The default model is `gpt-6-luna`.** The built-in client and the CLI default to `gpt-6-luna` at medium reasoning with a 25,000-token completion allowance. `gpt-4o` and `gpt-4o-mini` remain supported with their zero-temperature and 4,096-token defaults.
- **The LiteLLM minimum is 1.102.0**, whose OpenAI adapter accepts the reasoning request arguments.
- **CLI profile files must be private.** The CLI creates `.profiles` and `.selected.profile` at mode 0600 and refuses either file if it is not regular, belongs to another user, or is readable or writable by group or other users. It creates the profile directory at 0700 and refuses an existing directory writable by group or other users. An existing 0755 directory is accepted with a warning and left unchanged.
- **Planning defaults allow large tables.** `plan.max_partitions` defaults to `20` (was `4`) and `plan.max_leaves` to `100` (was `24`); `plan.max_depth` stays `2` and `plan.target_rows_per_leaf` `50`. Large tables need the capacity: their plans can need more than 24 leaves, or more than 4 children for one split, and the old caps stopped them there. `plan.mode` still defaults to `flat`, so a request that does not ask for a split is unchanged.
- **Planning bounds follow the shape of the tree, not the leaf cap alone.** The published worst-case counts, and the new `planning.leaf_limit`, count only the split proposals and leaves the tree can reach, so at the defaults a partitioned request is bounded at 21 proposals and 100 leaves rather than 199 proposals. [Decomposition](lib/README.md#decomposition) gives the counts; the coordinator's behavior is unchanged.
- **`o1` and `o3-mini` are sent as reasoning models.** They had no request profile, so they were sent a 4,096-token `max_tokens` and no reasoning effort. They now get `reasoning_effort` (default `medium`), no temperature, and a 25,000-token allowance sent as `max_completion_tokens`, which also raises the floor a cost ceiling on them has to clear. A `temperature` set for either is refused before anything is spent.
- **A bare name LiteLLM cannot route is refused before spend.** The package names OpenAI as the provider for its own models and for bare names in OpenAI's families (`gpt-`, `chatgpt-`, `o` and a digit). Any other bare name is sent as configured, and if the installed LiteLLM cannot tell which provider serves it, the call now fails with an uncharged `ConfigError` asking for a `provider/model` name, rather than failing inside a charged attempt. Only an OpenAI-family name is pointed at `openai/`.
- **Cost reported under a ceiling on GPT-6 and GPT-5.x is a usage bound, not the whole reservation.** Such a call is charged the most its reported usage could have been billed, where the response proves each input, and still reports `accounting_known=False`; [the cost bound](lib/README.md#the-cost-bound) states the rule.
- **A call on a model outside the table, or at caller-supplied rates, keeps its reservation under a ceiling.** The calculator's figure for it cannot be checked against rates this package publishes, so it no longer releases the reservation; the greater of the two is charged, with `accounting_known=False`. Without a ceiling a readable calculator figure is still reported as measured.
- **The cost bound carries OpenAI's regional-processing uplift.** Models OpenAI charges 10% more for regional processing (GPT-6, GPT-5.6, GPT-5.5, and the GPT-5.4 family) are bounded with the uplift included, because a response does not say whether it applied. The floor for the default `gpt-6-luna` at 25,000 tokens is about $0.01375.
- **Rates supplied for a model in the table no longer drop its known charges.** `llm.price_per_input_token` and `llm.price_per_output_token` replaced the table outright, so supplying `gpt-6-sol`'s published base rates bounded it without its cache-write rate or the regional uplift, below the table's own bound. For a table model they are now read as base rates: the entry's cache-write ratio, long-context tier and regional uplift apply to them, and the bound is the greater of that and the table's. Rates for a model outside the table are used as given and must cover every tier it can be billed at.
- **A name the table does not carry gets no defaults.** No default effort or temperature is sent for it, and its allowance goes as `max_tokens` for LiteLLM to translate.
- **Per-token rates print as the published decimals.** `model inspect` printed values such as `2.0000000000000002e-07`; the rates are now derived from the listed decimal and print as `2e-07`. No rate changes beyond float rounding.
- **The version was 2.1.0 in all three packages**, and the CLI and MCP server required `blue-data-llm-source[llm]>=2.1.0`.

**Removed**

- **The `claude-3-5-haiku`, `claude-3-5-sonnet` and `claude-3-opus` price rows.** The `openai` variant cannot call them, so listing them among the models a cost ceiling can be bounded against was wrong, and the hint for them pointed at `openai/`. The OpenAI legacy rows, `gpt-4`, `gpt-4-turbo` and `gpt-3.5-turbo`, stay.
- **`-v/--verbose` on `blue-llmdb data estimate`.** It changed nothing about the estimate; it remains on `data query`.

**Fixed**

- **Past 10,000 attempts, a ceiling set to the published `max_cost` refused the last one.** The estimate multiplied where the ledger adds, and the product can land a hair below the ledger's sum. With retries now capped, `max_cost` and `attempts_within_ceiling` both come from the ledger's own in-order sum, so a ceiling equal to `max_cost` admits every attempt it counts.
- **`lib/scripts/install.sh` pointed at an internal package index for `blue-data`.** It is installed from a checkout, as `docs/installation.md` says, and the message now says so.
- **Published planning counts left out most planning calls.** `planning.planned_logical_calls`, `planned_provider_attempts` and `request_calls` charged one bootstrap call whatever the schedule, and `request_calls` charged nothing for split proposals, so a `planning.cardinality_first` request made more calls than the count said. They now take `planning_order` and `distribution_search`, defaulting to the source's own schedule, and count every stage: the schedule's fact calls (new `planning.fact_calls`), then the split proposals or the distribution calls, then the leaves. `planning.planning_model_calls` publishes the planning part alone. `planning_calls` and `worst_case_attempts` already bounded every schedule and are unchanged.
- **MCP errors quoted deployment values back to the caller.** A malformed `BLUE_DATA_LLM_SOURCE_*` value appeared in the error returned to the MCP client, and a value the library refused came back inside the library's own message. Masking credential-shaped text did not cover an arbitrary private value. Errors now name the variable and what it must be, and a configured model name the package does not publish, and the cache directory, are masked in every result and error.
- **Numbers written with thousands separators lost the whole answer.** A model answer such as `"population": 4,470` is not valid JSON, so `parse_records` raised `ParseError` and every record in the response was discarded. When strict parsing fails, a bare number in an object value that is grouped by commas in threes now loses its separators and the text is parsed again under the same strict rules; strings, keys and array elements are never touched, and a response that still fails raises the original error. `meta.repaired_numbers` counts the numbers read this way.
- **`gpt-6-sol` and other new OpenAI names failed on provider resolution.** LiteLLM's bundled price map does not know them, so it could not tell which provider to use, and the failed attempt still kept its reservation. Bare OpenAI names are now sent with the provider named.
- **A `$0` calculator result was reported as a measured cost.** LiteLLM returns `0.0` for a model its price map does not carry, and the package took that as a measured free call, so a ceiling released every reservation, its running total never grew, and the result reported `accounting_known=True` at `$0.0000`. A calculator zero for any call that reached the provider is now an unknown cost, whatever its usage block says, since every request sends a prompt; only a cache hit keeps its zero.
- **All-zero token counts could release a reservation.** Under a ceiling, a response carrying text beside zero prompt and completion counts built a usage bound of zero, so repeated responses of that shape settled billed calls at nothing and let `limits.max_cost` be passed. The usage bound now requires at least one prompt token, and at least one output token when the answer has text; counts that cannot describe the call keep the reservation.
- **`gpt-4o-2024-05-13` was priced as `gpt-4o`.** The dated-name match gave it `gpt-4o`'s $2.50/$10 per million tokens, while OpenAI bills it $5/$15, so a ceiling on it was bounded too low. It has its own row, and a dated name now resolves to the longest matching table name.
- **The MCP server ignored its documented deployment configuration.** It built its source with no properties, so a deployment could not choose the model, the allowance, or the rates a ceiling is bounded against, whatever its documentation said about the server being configured where it is started. It now reads the variables listed under Added.
- **A source rebuilt from the registry treated recorded defaults as the caller's choices.** `LlmSource.properties` held the package defaults (in 0.2.0.0: `gpt-4o`, a 4,096-token allowance, temperature 0, no streaming), and `DataRegistry.register_source` records those properties. `connect_source` rebuilt the source with them as explicit settings, so a rebuilt source kept them even where its model or an injected client called for others. Defaults are now applied per call for the model that call resolves to.

## 0.2.0.0 — released (as 2.0.0)

Version 0.2.0.0 replaces the command-line interface, renames and expands the MCP tool set, adds user documentation, and standardizes repository packaging. It has three breaking changes: the CLI name and command structure, the MCP tool names, and the accepted contents of a `properties` map.

**Added**

- **Breaking: the command line is `blue-llmdb`, twelve commands over four components.** It was `llm` with `fetch` and `info`. The new tree is `profile add|remove|list|config|inspect|select`, `data query|estimate`, `model list|inspect|select` and `metadata inspect`, in the `<cli> <component> <action>` shape the rest of the Blue family uses. The old `llm` entry point is removed rather than aliased. What this exposes that was previously reachable only from Python: `data estimate`, which prices a request without contacting a provider; the `model` component, which says which models carry a published price and whether a cost ceiling can be bounded against one; and most of the adapter settings, which had no flag at all.
- **Profiles and environment-based configuration.** Profiles live under `~/.blue-llmdb/`, relocatable with `BLUE_DATA_LLM_SOURCE_HOME`. Twenty `BLUE_DATA_*` environment variables are supported. Settings resolve in the order command option, environment variable, profile, then built-in default; `--help` documents that order. `blue-llmdb profile inspect` shows the resolved values and their sources, with secret-shaped values masked. Missing named profiles and empty exported values such as `BLUE_DATA_LLM_MODEL=''` are rejected so a misspelling cannot silently remove configured ceilings.
- **`--format table|json|nl|csv` on every command that returns a result, and `--version`.** `table` is the default. `--format json` writes only the result object to standard output, so it can be piped.
- **Coded errors.** Errors use one line on standard error, `ERROR: <CODE> <message>`, with nine codes over exit statuses 1 through 8 and 0 for success. Parser and library failures use the same format. Under `--format json`, errors raised after argument parsing also produce `{"error": {"code": ..., "message": ...}}` on standard output. Parse failures occur before a format can be selected and therefore use only standard error.
- **Two MCP tools for the price table.** `llmdb_list_models` gives the model names this package carries a published price for, and `llmdb_inspect_model` gives one model's rates and whether a `limits.max_cost` ceiling can be bounded against it. Both are offline and free. A cost ceiling is refused before the first call when the configured model has no published rates, and until now the only way to learn that was to have a query refused.
- **User documentation under `docs/`.** The documentation now includes an [index](docs/README.md), quick start, interface references, task guide, API reference, and extension guide. The root README links into this set. CLI and MCP references are in [`docs/cli.md`](docs/cli.md) and [`docs/mcp.md`](docs/mcp.md); contributor documents are under `design/`.
- **The MCP package carries `build.sh` and `publish.sh`.** It shipped `install.sh` alone, so it could be installed from a checkout but not built or published the way the library and the CLI are. The two scripts are the ones the other packages already use.

**Changed**

- **Breaking: the MCP tools are renamed.** `llm_fetch`, `llm_estimate` and `llm_info` are now `llmdb_query`, `llmdb_estimate` and `llmdb_inspect_metadata`. The old names are removed rather than aliased; a client still calling one gets `UnknownTool` naming every tool that does exist. A client holds one flat tool namespace and this family ships a server per source, so every name here carries this server's own prefix and the action half matches the command line's verb for the same operation.
- **Breaking: six public names and two serialized `prompt_version` values are renamed.** The replacement names identify the returned call bound, the leaf-fetch prompt, and whether the prompt includes an ordered primary key and optional row estimate. The old names are removed without aliases.

  | Old | New |
  |-----|-----|
  | `planning.initial_v2_logical_calls` | `planning.planned_logical_calls` |
  | `planning.initial_v2_provider_attempts` | `planning.planned_provider_attempts` |
  | `prompts.build_initial_v2_fetch_prompt` | `prompts.build_leaf_fetch_prompt` |
  | `prompts.INITIAL_V2_FETCH` | `prompts.LEAF_FETCH` |
  | `prompts.INITIAL_V2_PROMPT_VERSION` | `prompts.KEYED_LEAF_FETCH_PROMPT_VERSION` |
  | `prompts.LEGACY_INITIAL_V2_PROMPT_VERSION` | `prompts.LEGACY_LEAF_FETCH_PROMPT_VERSION` |
  | `prompt_version` value `research-v2-runtime-1` | `keyed-leaf-fetch-1` |
  | `prompt_version` value `initial-v2-1` | `leaf-fetch-1` |

  These values appear in serialized `LeafTask` payloads and in the leaf prompt's `Prompt contract:` line. A stored 0.1.2.0 task carrying `research-v2-runtime-1` is refused as an unsupported `prompt_version`. Rebuild the task from the plan instead of replaying the stored dictionary.

  **Migration for the renames.** Change the import and the call: the signatures, the return types and the computed figures are identical, and a partitioned plan's bound is the same integer it was. `planned_logical_calls` and `planned_provider_attempts` are exported from `blue_data_llm_source.planning`, and `build_leaf_fetch_prompt` from `blue_data_llm_source.prompts`, at the same paths as before. A caller comparing a `prompt_version` against a literal should read the constant instead.
- **Breaking: the `planning.research_order` schedule is `planning.cardinality_first`.** It asks for cardinality before schema. The old value is removed, not accepted as a synonym.

  | Old | New |
  |-----|-----|
  | `planning.PLANNING_RESEARCH_ORDER` | `planning.PLANNING_CARDINALITY_FIRST` |
  | `plan.planning_order` value `planning.research_order` | `planning.cardinality_first` |

  This value is published, not only imported. It is a `plan.planning_order` entry in `properties`, the argument to `--plan-planning-order`, and a JSON Schema `enum` member the MCP server advertises on `llmdb_query`, so a client that reads its arguments out of the schema picks the change up on its next tool listing. It is also recorded in a planning receipt as `planning_order` and checked when a receipt is read back, so a receipt written by 0.1.2.0 is now refused the way any unrecognized order is. Sending the old string raises `ConfigError` naming the five accepted values.

  **Migration for the planning order.** Send `planning.cardinality_first` where `planning.research_order` was sent, in `properties`, on `--plan-planning-order`, or as an MCP argument, and import `PLANNING_CARDINALITY_FIRST` from `blue_data_llm_source.planning` where `PLANNING_RESEARCH_ORDER` was imported. The schedule does not move: the same three stages run in the same order, from the same prompts, under the same bound of three planning calls. A caller holding a stored receipt re-derives it from the plan.
- **The server reports its own version and instructions in the handshake.** It returned the protocol SDK's version, because the server was constructed without one.
- **Output that quotes text this package did not write is masked.** An error line, the JSON error object, a `--log` line, the traceback `--log` prints, an MCP tool's error text, the model name `llmdb_inspect_model` echoes, the `reason` an unbounded estimate gives, and in a run's `meta` the `model`, `requested_attrs`, `asked` and `unchecked_types` fields all leave through a new `redact`, exported from `blue_data_llm_source`. It replaces two things with `***`: a value the environment holds under a credential's name, and text written in the shape of a key. A provider SDK can put the request it sent, headers included, into an exception message, and both interfaces printed whatever arrived. What a caller may notice: a message quoting a long opaque string now shows `***` where the string was, and `meta.model` reads `***` on a deployment that configured a credential as the model name. The CLI masks its own two copies of that name for the same reason — the model in the table footer and in the `nl` sentence, which read the metadata field rather than the view, and the `llm.model` entry in the `settings` envelope, which is the value the caller supplied. Nothing else in `settings` is masked: a cache directory is a path, and a path carries enough entropy to read as a key shape on an ordinary machine. Records are not masked, and neither is a diagnostic naming the keys the model returned — this source returns model output as data, and a record value that reads like a token is the answer. `requested_attrs` is the one diagnostic masked anyway: it does index the records, but it is the caller's own text handed straight back. A coverage test examines every string published by a view or tool result and requires it to be masked or explicitly exempted, so a new field must declare which rule applies.
- **The two model tools agree with each other and with the library.** `llmdb_list_models` described itself as the model names a ceiling can be claimed against, which reads as exhaustive and is not: a dated variant prices against the base it extends, so `gpt-4o-2024-08-06` is bindable and was never on the list. The tool now says it publishes pricing bases, and the README and the interface specification say the same. `llmdb_inspect_model` called `can_bound` without the source's properties, so a deployment that supplied `llm.price_per_input_token` and `llm.price_per_output_token` was told `cost_ceiling_supported: false` while `llmdb_estimate` on the same source returned `bounded: true`. It now evaluates the properties a fetch would run with. `priceable` is unchanged and still reports the price table alone.
- **A value outside a declared set is no longer read back in the MCP refusal.** A bad `plan.mode` was answered with the accepted values and `got '<what you sent>'`; the message now stops at the accepted values, which is the half the caller could not work out. An unknown *key* is still quoted, because a misspelling is the one thing a caller has to be shown to find.
- **The MCP schemas declare the non-blank and uniqueness rules the library already enforced.** `attrs`, `plan.key`, `plan.keys` and `plan.partition_key` carry a `pattern`, and `attrs` and `plan.keys` carry `uniqueItems`. `attrs: ["   "]`, `attrs: ["country", "country"]` and a repeated `plan.keys` entry validated against the advertised schema and were then refused by the library a moment later; a client generating arguments from the schema can now tell beforehand. `attrs` takes a bare name or an object, so `["country", {"name": "country"}]` is one attribute named twice in two shapes and no JSON Schema keyword can express that; the server refuses that pair itself, as `InvalidArguments`, before the model is reached.
- **`plan.mode`, `plan.schema_mode` and `plan.planning_order` advertise their allowed values as a JSON Schema `enum`.** They carried them in description prose, so a client could not discover them mechanically. Root-level `required` is now enforced as well as advertised.
- **Breaking: a key `properties` does not define is refused rather than ignored.** `llm.*`, `limits.*` and `plan.*` were each a closed set; anything outside all three was accepted, dropped, and the request ran as though it had never been set. `properties={"llm_fn": my_model}` is the shape that cost money: it reads to a caller as an injected client, and the request went to the default one and the provider instead. The accepted map is now closed too: those three namespaces plus `connection`, `cache_store`, `budget` and `usage_sink`. Anything else raises `ConfigError` naming the key and listing what is accepted, before a client is resolved and before any provider contact. This reaches `fetch`, `afetch`, `estimate`, and `optional_properties` on `execute_query`, `execute_query_nl` and `execute_nl_tool`. A key that is not a string is refused the same way, naming the key and the type it is, rather than arriving as an `AttributeError` raised inside a check.
- **Breaking: `llm.model`, `llm.max_tokens`, `llm.temperature` and `llm.timeout` are value-checked where the key set is.** The names were accepted and the values were not read. `llm.max_tokens=0`, `-5`, `1.5` and `'many'` all reached the provider as written, because the only check on the output allowance lives in the cost bound and that path does not run unless `limits.max_cost` is set — so an unbounded request carried a bad allowance into a billed call. `llm.model=123` was the same hole with no number in it: the call builder asks whether the name is truthy, so `123` went to the provider as a model to call. Each key now takes the bound its reader already has: `llm.model` is a non-empty string or `None` for the default, `llm.max_tokens` is a whole number of at least 1 or `None` for no cap, `llm.temperature` is a finite number, and `llm.timeout` is a finite positive number of seconds. All four raise `ConfigError` naming the key and the value, at the same boundary that refuses an unknown `llm.*` name, so an injected client and an `llm_fn` are covered too. No numeric range is placed on temperature beyond finiteness: the usable span differs by provider, and refusing a value the provider accepts would be worse than the silence. The CLI already refused a sub-1 `--max-tokens` and needs no change. A caller passing a placeholder allowance, or a temperature of `float('nan')`, is refused before a client is resolved rather than at the provider.
- **The `LLM.ESTIMATE` op reads the request the way `LLM.FETCH` does.** `execute_query` read an estimate's `attrs`, `attr_names` and `context` from the query spec only, so the same fields supplied in `optional_properties` were accepted and dropped and the figure priced a request without them — an understatement the caller has no way to see. Both ops now read all three from both places, with `optional_properties` winning over the spec, which is the precedence `LLM.FETCH` already had. `max_records` is the one field an estimate cannot honor, because the model is asked once and the surplus records are dropped on arrival; it now raises `ConfigError` on that op instead of being swallowed. The CLI already refuses `--max-records` on `data estimate` and the MCP `llmdb_estimate` schema already excludes it, so neither changes.
- **The registry's own `_class` key is accepted.** `blue_data.registry.DataRegistry.register_source` records it beside a source's properties and `connect_source` reads it back to rebuild the class, so a source that has been through that round trip arrives carrying a key this package never set.
- **Migration.** `llm_fn` is a parameter of `fetch`, `afetch`, `estimate` and `execute_query_nl`; pass it as one. `attrs`, `context` and `max_records` are parameters of `fetch` too, and `execute_query` and `execute_query_nl` still read them out of `optional_properties`, where the data-layer signature has nowhere else to put them — but they are refused in `fetch(properties=...)`, which has the parameters. Any other refused key was already doing nothing, so deleting it changes no behavior. An injected client's own `properties` are checked together with the caller's, as they already were for the three namespaces, so a client that keeps private configuration under a key of its own has to keep it off that map. A `max_records` sent with an `LLM.ESTIMATE` op has to go: it never moved the number. The CLI and the MCP server send only keys inside the accepted set and need no change.
- **The design documents move from `docs/design/` to `design/`.** Links and tests that read them by path follow the move. Earlier release entries retain their original paths.
- **The platform services are `platform/llm-cli/` and `platform/llm-mcp/`.** A service directory under `platform/` is named for its family and its service. The import packages `blue_data_llm_cli` and `blue_data_llm_mcp` and the distribution names `blue-data-llm-cli` and `blue-data-llm-mcp` are unchanged, so nothing a caller imports or installs moved.
- **`.gitignore` ignores `*.envrc`, not `.envrc` alone.** The bare name matched one file; a direnv file named anything else was left for someone to commit.

## 0.1.2.0 — released (as 1.2.0)

A minor release with opt-in planning features and compatibility-oriented behavioral repairs.

**Added**

- **The CLI has bounded effort levels.** `--effort low|medium|high` maps to zero, one, or two
  continuations, allowing up to one, two, or three logical extraction asks per part when a primary
  key is available. An explicit `--plan-continuations` value wins. Retries remain separate provider
  attempts. Flat `medium`/`high` requests without a declared key fail before source construction.
- **CLI machine output stays machine-readable.** Provider dependencies sometimes write diagnostics
  through Python's `sys.stdout`. The CLI now redirects those writes to standard error while a fetch
  runs, covering the known provider banners. Direct file-descriptor writes and output produced after
  the fetch returns are outside the redirect.

- **Non-flat planning introduces bounded local task trees.** Non-flat
  requests bootstrap a retrieval query and schema, then `partitioned` can split useful descendants
  breadth first. `row_by_row` uses an explicit entity list or a bounded enumeration. Planning falls
  back to the intact parent slice when a proposal is invalid, incomplete, or unaffordable.
- **Four hierarchy controls are public on Python, CLI, and MCP:** `plan.max_depth` (default `2`),
  `plan.max_partitions` (default `4`), `plan.target_rows_per_leaf` (default `50`), and
  `plan.schema_mode` (`preserve` by default or `enrich`). `plan.partition_key` constrains the root
  proposal only; descendants may choose other dimensions.
- **Non-flat requests can infer a schema.** Preserve mode keeps a nonempty caller schema unchanged.
  Enrich mode may append inferred attributes while retaining every caller name, type, and key.
  `meta.requested_attrs` remains the caller declaration, while output records follow the effective
  schema.
- **`meta.row_estimate` reports the accepted bootstrap root hint.** It preserves an estimate of zero
  and is `None` for flat mode, an unknown estimate, or a discarded bootstrap transformation. CLI and
  MCP machine metadata always include it; the CLI table footer prints the value or `unknown`.
- **`meta.stop_reasons` retains simultaneous stop facts** as an ordered distinct list.
  `meta.stopped_by` remains the highest-precedence projection. CLI and MCP machine output always
  include `stop_reasons`, `gaps`, and `requested_attrs`; CLI table output prints every stop reason
  without requiring `--verbose`.

- **A request can be decomposed into parts.** `plan.mode` selects `flat` (the default), `partitioned`, or `row_by_row`. Non-flat modes add bootstrap planning, and partitioned mode may add one proposal call per eligible slice before leaf extraction. `flat` makes no planning call, so a caller who sets nothing retains the one-completion path.
- **`plan.max_leaves` bounds the terminal slices in a plan.** A proposed expansion that cannot fit is rejected as a whole and the unchanged parent becomes a leaf. A row-by-row enumeration that cannot fit falls back to the unsplit batch request rather than executing a prefix.
- **A part can ask again for records it did not get**, bounded by `plan.max_continuations`. `0` by default, so each part asks once unless you raise it. It bounds asks per leaf rather than billed attempts or planning calls; each ask may still be retried up to `limits.max_retries` times.
- **`plan.key` names the attribute identifying a record**, so parts returning the same record merge rather than duplicating it. Without one, records from different parts are not merged, and exact whole-record duplicates are still removed.
- **`meta.gaps` says why rows may be missing** when the source observed an operational failure, fallback, interruption, or discard. An empty list means no supported diagnostic fired. It does not mean the answer is complete.
- **A response that ends mid-record keeps the records it completed.** An incomplete document used to discard the whole answer and raise, losing records already paid for.
- **`plan.partition_key` guides the root proposal.** Descendants may split on another useful dimension and cannot repeat an ancestor dimension.
- **Python, CLI, and MCP share 14 standard planning settings.** The CLI uses `--plan-*` flags and MCP uses
  the library's dotted property names on `llm_fetch`: mode, continuations, leaves, singular and
  composite keys, exact rows, exclusion bytes, root partition key, depth, partitions, target rows,
  schema mode, planning order, and estimate exposure.
- **Direct Python callers can opt into rule-backed distribution search.** The three additional
  controls are `plan.distribution_search`, `plan.identity_partitions`, and
  `plan.max_strategy_candidates`. Distribution search requires partitioned mode, explicit ordered
  `plan.keys`, finite declared identity rules, and at least one root-applicable rule. Invalid inputs
  fail before provider contact; per-call rules replace source rules; all three distribution-search
  controls are stripped from provider properties. A direct fetch with distribution search enabled
  can carry a versioned `PlanningReceipt`. CLI and MCP do not expose distribution search or the
  receipt in this release.
- **Direct Python also retains `plan.max_excluded_keys`.** This count bound complements the shared
  encoded-byte bound on continuation exclusions. CLI and MCP use its default and do not expose a
  separate control for it.

**Changed**

- **The public `source.decide_outcome` rule now accepts planning-aware execution facts.** Existing
  four-argument calls retain their behavior. Keyword-only `answered`, `interrupted`, and
  `stop_reasons` facts let the runtime report an answered but interrupted result as `partial`, while
  retaining simultaneous limits in the stop fields. `LlmSource` uses this public rule directly.

- **`meta.stopped_by` names the highest-precedence stop.** `meta.stop_reasons` preserves the other simultaneous limits. A partial run keeps `outcome=partial` while the stop fields report any cap; a retained result cut only by `max_rows` reports `truncated`.
- **`meta.outcome` reports `partial` when extraction was answered but some work was interrupted.** This includes a failed split leaf beside an answered sibling and records retained before a late flat continuation failure. Simultaneous caps remain in `stop_reasons`. The CLI exits `8` for partial results.
- **`meta.record_origins` names which parts produced each record**, parallel to `records`, a list per record because overlapping parts can each return the same one.
- **`meta.asked` reports the question that actually ran** when an analysis call restated it, and is absent when nothing changed.
- **`meta.gaps` is always present in machine-readable output**, empty list included, so a program branches on what it says rather than on whether the key arrived.
- **Filters carry their own shape.** A part's constraints are `Exact` or `OneOf` rather than plain text, and reach the model with the operator said outright: `- field "region" must equal one of ["A, B", "C"]`. Joined into one string, a value containing the separator was indistinguishable from two values.

**Known limits**

- **Splitting preserves the enumeration it was given, not the coverage of the answer.** Each distinct alternative the analysis enumerated is encoded in exactly one part's filter. The enumeration itself comes from a model and may be wrong, the alternatives may overlap, and a model may omit records from a filter it was given correctly. None of that is checkable from here.
- **A continuation cap that fires after a productive answer means completeness was not established, not that another record exists.** A model with one row left and a model with a thousand answer the last permitted call identically.
- **An output-limit cause is reported only where the provider attested one.** `provider_output_limit` requires a recognized termination reason; without it a response that did not parse whole is `response_incomplete`, which says what was observed and nothing about why. A caller-supplied `llm_fn` can never attest, so it never gets the stronger name.
- **Planning protects one next extraction rather than admitting the whole worst case.** Each optional planning call is checked against current call, cost, and deadline headroom. Actual provider attempts still claim the shared budget atomically, so later leaves may remain unserved.
- **A model rewrite can still broaden or narrow the request.** Outside `flat`, an analysis call restates the request and that restatement is what runs. The prompt instructs against changing the meaning, which is an instruction and not a check. `meta.asked` reports the question that actually ran whenever it differs from the one you typed, so the substitution is visible rather than prevented.
- **Encoding model text into prompts prevents it becoming a new instruction line. It does not make it inert.** Values, names, held records and the query are all encoded, so none can open a line of its own; nothing here stops a model from being influenced by instructions sitting inside data it is shown. The caller's own `context` is inserted raw, deliberately: the caller is the principal.
- **`meta.record_origins` names the parts that returned a record.** It does not claim they are the only parts that hold it.
- **A split request where every part came back unanswered for mixed reasons raises, and the ceiling that also fired is not reported.** Nothing was answered, so there is no partial result to carry it, and the exception belongs to the provider rather than to this library — writing the axis onto it would mutate an object a client may raise more than once. The failure is what a caller receives; the ceiling is visible only in the budget they supplied.

- **`estimate` prices one flat fetch, not a decomposed request.** It reads no `plan.*` setting, and its figures cover the retry allowance of a single flat fetch. Bootstrap, proposal, enumeration, leaves, and continuations can make a non-flat request cost more. The planner reports its configured worst-case call bounds separately.
- **Worst-case plan counts are diagnostics, not an admission reservation.** Flat work and optional continuations are admitted one provider attempt at a time. Non-flat planning uses bounded local look-ahead so it does not spend the last affordable call on an optional planning step.
- **A planning receipt proves internal agreement, not answer quality.** It binds configured rule
  digests, planning facts, and the serialized fetch plan. It does not prove rule authenticity,
  factual truth, completeness, or improvement over another method.

## 0.1.1.0 — released (as 1.1.0)

**Added**

- Spend ceilings and a cost estimate over MCP. `llm_fetch` accepts `limits.max_cost`, `limits.max_seconds` and `limits.max_calls`, and a new `llm_estimate` tool answers what a request could cost without contacting a provider. Until now that transport accepted a row cap and nothing else, so a caller reaching the library over it could spend without a per-call ceiling.
- `llm.stream=True` is supported. It was accepted as a key and refused by value, which shut out every caller whose provider configuration or proxy requires or defaults to a stream. **It does not make a fetch faster and is not there to.** A fetch parses one whole JSON document into records, so nothing can be handed back before the last chunk arrives; the chunks are read to the end, reassembled by the provider library's own helper, and passed to the same path a non-streamed response takes, on the synchronous and the asynchronous entry point alike. Pricing, reservation settlement, row counting, caching, and usage recording are unchanged.

  The accounting has one visible consequence. A provider sends token counts with a stream only if it chooses to, and when none arrive the call cannot be priced: the reservation stays at the bound claimed for the attempt instead of settling, the usage record reports `cost_known=False`, and the fetch reports `accounting_known=False`. This is the treatment every unreadable cost already gets, and it is deliberate — the assembler will supply a usage block counted from the text by a local tokenizer, and pricing that would settle a figure the provider never charged and leave a cost ceiling admitting attempts against a total that never moved.
- The four orchestrator tools this source can actually serve are advertised again: `list_databases`, `list_collections`, `get_schema` and `execute_query`. The definitions come from the base class rather than being restated, so their schemas cannot drift from what its dispatcher expects. `execute_query` is the one that spends, and a ceiling passed through `optional_properties` binds it. Any other tool name is refused by name, and the tool-driven query loop stays refused because it drives provider calls this source's ceilings do not govern.

**Changed**

- `llm.rate_limit` is still refused, and the refusal now defers it to 0.2.0.0. The 0.1.0.0 entry below named 0.1.1.0, which is this release, so a caller who read that message and upgraded arrived at the version they were already running. Nothing about the refusal itself changed, and the reasons the key was withdrawn are unchanged; `lib/README.md` states them.

**Fixed**

- The MCP argument checker had no branch for number-typed fields, so one reached the library with neither its type nor its minimum enforced. Nothing had exercised it because no shipped field was number-typed until the cost and time ceilings arrived.
- `blue-data-llm-cli` and `blue-data-llm-mcp` exported the `__version__` of 0.1.0.0 while their packaging declared 0.1.1.0, so anything introspecting an installed interface package read the previous release. The version test now compares each package's packaging metadata against the version its module exports, rather than the library's alone.

## 0.1.0.0 — released (as 1.0.0)

First release. The package extracts the earlier language-model source into a standalone repository that depends on the data layer and inherits its `DataSource` base class, without depending on the orchestration layer above it.

**Added**

- `LlmSource` with `fetch` and `afetch`, plus `execute_query` and `execute_query_nl` matching the data layer's source signatures.
- `blue-data>=0.1.0` as a core dependency alongside `tenacity>=9.0.0`. `LlmSource` inherits `blue_data.source.source.DataSource` directly, as every source in the layer does. Base-class order determines which implementations resolve. Most of the base methods return an empty result rather than raising, so one left unoverridden here answers nothing instead of failing. The transaction methods instead raise `NotImplementedError` naming this source, and the orchestrator-tool methods carry behavior that requires three local overrides: `get_nl_tools` and `execute_nl_tool` are narrowed to the tools this source can answer, and `execute_query_nl_tools` is refused. A test asserts that each method on the shared surface resolves to this class. `blue-data` brings `pandas`, `numpy`, and `jsonpath-ng` with it. Nothing here imports `blue` or `blue_data_ops`, and a test asserts that too.
- `estimate()` and the `LLM.ESTIMATE` op: what one fetch could cost at most, built from the prompt this source would actually send and without contacting the provider. `Estimate` carries `bounded`, `max_cost`, `reason`, `model`, `prompt_bytes`, and `max_output_tokens`, and a model this package cannot price comes back with `bounded` false and a `reason` rather than raising. It is the same bound the reservation claims, so an estimate and the ceiling that enforces it cannot disagree. The op returns the estimate as a one-record list, since that is what the query surface returns. `Estimate` and `OP_ESTIMATE` are exported from the package root.
- A ceiling as an input to the query. `execute_query` and `execute_query_nl` take `optional_properties`, and a `limits.*` key placed there is merged over the instance's properties for that call alone and is not written back, so it binds the request it arrived with and does not leak into the next.
- `ExecMeta.outcome`: an empty result carries the reason it is empty, from a closed vocabulary of `ok`, `empty_query`, `model_returned_none`, `filtered_to_empty`, `stopped_by_limit`, and `truncated`.
- Budget ceilings on rows, time, cost, calls, and retries. The time ceiling bounds admission and cooperative waits rather than the whole run, and `lib/README.md` states the exclusions. Calls, time, and cost are claimed before the provider is contacted; `Budget.reserve` returns a `Reservation` that is settled against the real cost, kept at its claimed bound when the cost cannot be read, or released for an attempt that never reached the provider. Every reservation resolves on every path out of an attempt, including a response that cannot be read. Every `Limits` field is validated on construction, and an unknown `limits.*` property key raises `ConfigError` listing the accepted set.
- `llm/pricing.py`: `bound_cost` produces a genuine upper bound on one call, from the prompt's length in UTF-8 bytes plus a framing allowance at the model's input rate plus the whole `llm.max_tokens` allowance at its output rate. Bytes rather than characters, because a byte-pair tokenizer merges byte sequences and can emit more tokens than the prompt has characters. It raises `ConfigError` rather than guessing when the model has no published price and none was supplied, or when the output allowance is not a finite positive number; `rates_for` returns `None` for an unlisted model, and `can_bound` asks the same question without raising. The floor of the bound is the output allowance alone, about $0.041 for the default model and 4096 output tokens, so a smaller `limits.max_cost` refuses every call.
- `llm.price_per_input_token` and `llm.price_per_output_token` as accepted `llm.*` overrides, consumed by the client and never forwarded, so a model `pricing.PRICES` does not carry can still be given a cost ceiling by whoever knows its rates. Both must be supplied together and both must be finite positive numbers.
- `types.Capability` and `types.BudgetAwareClient`: a client declares which axes it can be held to through `budget_capabilities()`, returning names from `CALLS`, `ROWS`, `SECONDS`, `COST`, `ESTIMATE`, or `ALL`. `ESTIMATE` is not a ceiling: it declares that the client can price an attempt in advance, which `estimate()` requires before it will return a figure. The run hands its budget down per call under the `budget` property. Each configured ceiling on an undeclared axis raises `ConfigError`; `limits.max_rows` still binds for any client. `DefaultLlmClient` declares every axis; `FunctionClient` declares rows alone, so a call, cost, or time ceiling over an `llm_fn` is refused rather than settled at zero or measured against one invocation of a callable that may make any number of provider calls.
- `budget=` on `fetch` and `afetch`, and `Budget.derive`: a caller-owned budget that accumulates across every call it is handed to, from which each fetch derives a child bounded by what the parent has left. This is the route for a total across a sequence of requests, where per-call properties are the route for bounding one. Retry depth narrows along the chain through `Budget.effective_retries()` like every other axis, and a child does not inherit its parent's `stopped_by`.
- A per-call usage sink. The source hands the client a list under the `usage_sink` property and reads this call's token counts and model name only from it, so two concurrent fetches through one reused client no longer report each other's tokens. Calls and cost continue to come from the budget.
- `source.decide_outcome`: one public ordered rule for `ExecMeta.outcome`. Any `stopped_by` wins, giving `truncated` when the row cap fired and records remain and `stopped_by_limit` otherwise; then records present is `ok`, nothing from the model is `model_returned_none`, and the remainder is `filtered_to_empty`.
- `ExecMeta.key_collisions`: two returned keys that map to one requested attribute no longer resolve silently. The first is kept and the second is reported with the value it carried. Two occurrences of the identical key inside one object are a different case and raise `ParseError` at any nesting depth, because there is nothing there to tell the two values apart by. The same attribute requested twice raises `QueryError`. Two requested attributes that merely normalize alike do not: the fuzzy index drops the entry it cannot separate, so exact keys still match and a fuzzy-only key is reported unmapped rather than assigned by guess.
- Four of the base class's orchestrator tools. `get_nl_tools` advertises `list_databases`, `list_collections`, `get_schema`, and `execute_query`, and `execute_nl_tool` serves them by delegating to the base dispatcher. The definitions are the base class's own, filtered by name rather than rewritten, so an advertised schema cannot drift from the dispatcher that reads it. A name outside the four is refused with a `ConfigError` listing what is available, and nothing on this path leaves the `LlmSourceError` hierarchy, which the base's `ValueError` on an unknown name and `KeyError` on a missing input do. `execute_query` is the one tool that reaches a provider, and it takes `limits.*` in `optional_properties` like the rest of the query surface; a misspelled ceiling key is refused on every tool rather than only on that one.
- A command-line interface and an MCP server over the same library.
- Spend ceilings and an estimate over MCP. `llm_fetch` accepts `limits.max_cost`, `limits.max_seconds`, and `limits.max_calls`, under the library's own key names, and passes them through as the call's properties — the same route `optional_properties` takes on the query surface and `--limit-*` takes on the command line. Each is claimed before the provider is contacted, and a crossed ceiling comes back as an empty record list with `outcome` of `stopped_by_limit` and `stopped_by` naming the axis. A new `llm_estimate` tool bounds what one `llm_fetch` of the same request could cost without calling the model, returning the `Estimate` fields; its two costs are published unrounded, unlike the spend in a fetch's meta, because rounding a bound can round it down and a figure a run can exceed is not a bound. The server's own argument check, which does the whole job of enforcing the advertised schema with the SDK's prevalidator off, gained the `number` type these ceilings use. `max_records` is still a row cap rather than a spend ceiling, and the server still constructs its source with no properties, so a call that names no ceiling has none.
- In-memory and on-disk cache stores.
- `llm.rate_limit` is refused with a `ConfigError` and deferred to 0.1.1.0. Client-side spacing must reconcile with per-attempt budget admission, and every arrangement tried let one corrupt the other; a key that is present and subtly wrong is worse than one that is absent and says so.

**Prompt**

- The fetch prompt is new in this package; `lib/COMPATIBILITY.md` records its behavior.

**Known limitations**

- Half the base class's tool surface is not advertised. `get_metadata`, `get_column_stats`, and `get_relations` would answer with an empty result and no explanation, and `get_sample` raises a `TypeError` from the base dispatcher, which passes `row_sample_size` to a `fetch_entity_stats` that takes no such argument. `execute_query_nl_tools` is refused outright: it drives a loop of up to ten provider calls this source's ceilings do not govern. `execute_query_nl` is the natural-language route, and unlike that loop its spend and time ceilings are enforced.

- Inheriting `DataSource` does not make the source reachable by protocol name. `DataRegistry.connect_source` reaches this source through the class path recorded by `register_source` rather than through protocol-name dispatch, so an instance is built once and handed to `register_source`, and the registration survives the object.
- The MCP server's ceilings are per call and nothing sets them for the agent. It constructs its source with no properties, so a call that names none is bounded by nothing.
- The CLI exposes no estimate command, so a caller sizing a request before running it uses the library.
- The provider library writes colored banners to standard output on some failure paths, so `llm fetch --format json` can emit lines the CLI did not print and break a pipe into a JSON reader.
